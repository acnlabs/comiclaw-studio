# 广义资产与分账：现状、卡点、可落地的顺序

**状态：** 设计讨论，未开工。需要两个产品决定 + 一个 AgentPlanet 答复才能动手。

## 1. 提法

只把角色、场景、道具当资产是狭义的。要做共创并分账，**参与成品过程的任何生产资料**——剧本、图像、音频、视频片段、配乐——都该有产权，都该能授权、能交易、能参与收益分配。

这个提法我认同。下面是它落地时会撞到什么。

## 2. 已经成立的部分：署名这本账早就在记

不需要为分账重新做归属。每一类生产内容都已经带 `authorUserId / authorAgentId / authorKey`：

| 内容 | 表 | 有署名 |
|---|---|---|
| 剧本 | `ScriptVersion` | 是 |
| 分镜 | `Shot` | 是（`ShotVersion` 挂在 Shot 下） |
| 成片 | `FilmVersion` | 是 |
| 角色 / 场景 / 道具 | `Asset` | 是，且已有产权（`ownerType/ownerId`）与登记 |

也就是说，「一部片子由谁的哪些贡献构成」这件事，今天已经能查出来。缺的不是归属，是**结算**。

## 3. 三个卡点，按严重程度

### 3.1 成品没有收入（最根本）

现在系统里的钱只有两条路：

- **支出**：用户付给 comiclaw 的生成费（`chargeWalletUsage`）
- **收入**：资产授权费（`AssetLicense`），进单一产权人的钱包

**作品本身不产生任何收入。** 分账要分的那笔钱，目前是零。

### 收入从哪来（已有答复）

成品要发布到 YouTube、TikTok 等外部平台，收入包括流量分成、付费观看、广告植入；并且资方可以带钱加入组织、提出需求，创作时就把广告带进去。

**这里面其实是两种形状完全相反的收入，必须分开设计。**

| | A. 平台流量收入 | B. 广告植入 / 资方委托 |
|---|---|---|
| 钱什么时候到 | 作品发布之后，按月 | **开工之前** |
| 金额 | 事前未知 | 事前已知 |
| 钱先落到谁手上 | 某个人/组织的**外部平台账号** | 可以直接在站内，用 Credits |
| 粒度 | 平台按频道结算，不按作品 | 按这一单委托 |
| 份额 | 只能事后按贡献追认 | **可以开工前约定** |
| 我们能控制的部分 | 很少 | 几乎全部 |

**A 的链条里至少三段不在我们手上**：平台的钱、平台的报表口径、以及把外部收入换成 Credits 或提现。更要紧的是，这笔钱先进的是某个人或组织的外部账号，然后才谈分配——那一刻起这就不只是技术问题，是信任问题：谁收、凭什么信他会分、不分怎么办。做 A 之前得先回答这个，而它不是代码能回答的。

**B 几乎可以整个在系统内完成**，而且它把最难的那一半消掉了：份额事先约定，就不需要事后追认谁贡献了多少。

### 已定：协作作品走官方账号，收益由 comiclaw 再分配

广告植入等有知名度之后再谈，先做平台流量收入。规则：

- **协作作品统一通过 comiclaw 官方账号发布**（YouTube / TikTok 等），收益进官方账户，再分给参与者
- **非协作的个人作品**，用户发到自己的平台账号，与我们无关

这条规则回答了 §3.1 里那个非技术问题（谁收钱、凭什么信他会分）：**comiclaw 收，comiclaw 分**。

**那就得按托管的标准来建。** 真金白银在到达创作者之前会停在我们账上，这不是可以含糊过去的实现细节，它决定几件事：

1. **每一笔分配都要能追溯到依据**：哪个作品、哪个平台、哪个结算周期、平台报表原文、当时的汇率。贡献者要能自己看懂"为什么是这个数"，而不是只看到一个到账通知。
2. **平台报表是事实，我们的计算不是**。YouTube 按频道付款、按视频报数；TikTok 的口径更模糊。所以"这个作品赚了多少"是**从报表导入的**，不是我们算出来的——报表要原样存下来，不能只存我们算完的结果。
3. **汇率与手续费要显式记账**。平台付的是美元，创作者拿的是 Credits，中间的换算和损耗必须落在账上，否则第一次有人对不上数就再也说不清了。

### 最关键的一条：份额要在发布时定，不是到账时定

平台的钱要等几个月才到。如果那时才开始讨论谁占多少，就是纠纷现场——参与者早已散去，贡献记录还在但记忆和预期已经不一致了。

所以：**作品发到官方账号的那一刻，就要把参与者名单与份额冻结成一份快照**，此后到账多少都只是往这份快照里填数字。这件事不需要等平台对接，今天就能做，而且它是整条链上唯一一件必须早做的事——别的都可以等钱真的来了再补。

### 成片本身也是一种资产

顺带一条几乎白送的收入：把成片登记成资产、定价、授权，走现有链路即可（待 §17.1 的 `video` kind）。但它分的是"别人拿你的成片去二次创作"的钱，不是"观众看片"的钱，两者别混。

### 3.2 一个商品只有一个卖家

AgentPlanet 的 Store 商品是单 `seller_id`，结算打给那一个主体。也就是说**即便是现在的资产授权收入，也无法按贡献拆分**——全额进登记产权人。

两条路：

- 请 AgentPlanet 支持成交时按份额多方结算
- 或者收益先进一个 Org，由 Org 再分给贡献者——但这需要一个"从 Org 钱包付给个人"的接口，我们现在没有，而且钱在我们手上停留一段时间，性质变了（我们变成了资金保管方），要慎重

### 3.3 登记表只认三种 kind

`asset_kind ∈ character | scene | prop`。剧本、音频、视频**在本地可以是资产，但不能登记、不能上架**，直到 AgentPlanet 加类型。

我们侧对这件事是 fail-closed 的：`assetKindFor` 认不出的类型，发布接口直接拒绝，不会本地声称一个没登记成功的产权。所以先加本地类型是安全的，只是它们暂时卖不了。

## 4. 一个建议：别把"广义资产"理解成"都塞进 Asset 表"

`Asset.type` 是个字符串，加 `SCRIPT / IMAGE / AUDIO / VIDEO` 本身很便宜。难的是把 `ScriptVersion` / `Shot` / `FilmVersion` 变成 `Asset` —— 它们深嵌在工作台的每一个面板里，一次性搬迁风险大、收益不明确。

区分两件事：

- **广义资产是产品性质**：任何生产资料都该有产权、能授权、能参与分账
- **统一到一张表是数据模型**：不是达成前者的必要条件

后者可以晚很久，甚至永远不必完全做到。剧本已经有署名，要让它参与分账，需要的是「贡献 → 份额 → 结算」这条链，不是把它搬进 `Asset` 表。

因此建议的顺序：

1. **新类型先服务于今天「没有地方安放」的生产资料**。注意不是「没有归属」——上传的文件最终都会落进某个有署名的记录（`AssetVersion` / `ShotVersion` / `FilmVersion` / 角色形象），归属并不缺。缺的是**独立存在的资格**：一首配乐在系统里根本没有字段可放，只能夹在某一版成片的视频里；一张反复使用的参考图只能重复塞进不同的资产版本。这类东西成为 `Asset`，收益是"它可以被单独指认、单独授权"，而不是"它终于有作者了"。
2. **剧本 / 分镜 / 成片保持原表**，通过一个共同的「贡献」读取视图参与分账——它们已经有 `authorKey`。
3. **成片可选登记为资产**（`asset_kind: video`，待 AgentPlanet 支持），这样"别人拿你的成片去二次创作"这条收入路走现有链路。

## 5. 需要决定的

**产品（你定）：**

1. ~~成品的收入从哪来？~~ 已定：平台流量收入。广告植入等有知名度再谈。
2. ~~谁收钱？~~ 已定：协作作品走 comiclaw 官方账号，收益进官方账户后再分配。
3. **份额怎么算？** 这是唯一还挡着路的决定，因为它会长进数据模型。贡献是异质的——剧本、角色、分镜、成片不能简单按条数比。几种可能：
   - 人头均分（最简单，也最容易让干得多的人不干）
   - 按环节固定权重（如剧本 30% / 角色 20% / 分镜 30% / 成片 20%），栏目层面统一
   - 按各人在该作品里被采用的内容量加权
   - 栏目主人逐作品指定
4. **什么算"协作作品"？** 需要一条能写进代码的判据。候选：属于某个栏目的 PUBLIC 项目 / 有一个以上署名贡献者 / 由 Org 主持。这条决定了谁在分配名单里。

**AgentPlanet（已在对接文档 §17 提出）：**

3. `asset_kind` 能否扩展到 `script / image / audio / video`？
4. 成交时能否按份额多方结算？若不能，是否有 Org 钱包对个人的付款接口？

在这四个问题有答案之前，写任何分账代码都是猜。
